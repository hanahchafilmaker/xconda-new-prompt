## ■ 20. 글콘티/오브젝트 정리 문서 → 블로킹 보드 등록 코드 + 프리셋 자동 생성

**이게 뭔지 한 줄로**: 대본을 정리한 "누가·뭐가·어디서 나오는지" 목록(글콘티, 오브젝트 정리표
등)을 주면, 블로킹 보드(3D 미리보기 도구)의 코드에 사람이 직접 타이핑해서 추가해야 했던
`PROP_SIZES`/`SPECIES`/`ROOM_PRESET` 같은 등록 항목과, 보드에 바로 붙여넣을 수 있는 프리셋
프롬프트 파일을 자동으로 뽑아준다.

**트리거**: 사용자가 대본·글콘티·오브젝트 정리 문서(범례에 🧍인물·🪑소품·🏚장소 같은 표시가
있거나, 인물/소품/장소를 나눠 정리한 표·목록)를 올리며 "블로킹 보드에 등록해줘" / "프리셋
만들어줘" / "PROP_SIZES에 추가해줘" / "보드용으로 정리해줘" 라고 요청하면 이 절차를 따른다.

**반드시 지킬 것**: 이 작업의 상세 분류 기준·코드 형식·프리셋 형식은 전부
`references/board-object-registration.md`에 있다. **그 파일을 먼저 읽지 않고 임의로 코드를
만들지 않는다** — px/m 환산, 크기 추정 비율, 크리처와 소품의 경계 같은 실수하기 쉬운 규칙이
그 안에 정리돼 있다.

### 한눈에 보는 흐름
1. 문서를 읽고 등장하는 모든 대상을 **사람 / 크리처(비인간 생명체) / 소품 / 장소 / 특수효과**
   다섯 갈래로 분류한 표를 먼저 보여준다 (애매한 건 【 】로 표시).
2. 사용자에게 분류가 맞는지 확인받는다 — 특히 "원혼"처럼 특수효과인지 크리처인지 헷갈리는
   항목이 있으면 꼭 짚어서 물어본다.
3. `references/board-object-registration.md`의 규칙대로 크기(px/m)·색(hex)을 추정해 표로
   보여준다.
4. 사용자가 보드 코드 파일(app.js 등)을 함께 올렸으면, 그 파일 안에서 같은 이름이 이미
   등록돼 있는지 검사부터 한다 (없으면 "충돌 검사는 생략했다"고 먼저 밝힌다).
5. 실제 파일에 넣을 수 있는 **추가분 코드 스니펫**(파일 전체를 새로 쓰지 않는다)과, 핵심(★)
   씬 위주의 **좌표 데이터**를 정리해 준다(XCONDA_v1 씬 .json 형식과 동일).
6. README/GUIDE에 이어 붙일 수 있는 표 형식의 안내 문구도 함께 준다.

이 5갈래 분류·크기 추정·코드 형식의 자세한 예시(실제 통과한 사례 포함)는 전부
`references/board-object-registration.md`를 참고한다.

## ■ 20-1. 글콘티 → 프롬프트 변환 시 씬 JSON 자동 생성 (기본 동작 — 요청 없이도 한다)

> **⚠️ v5에서 바뀐 것**: v4.5까지는 프리셋 `.txt`, v5 초안에서는 편집기 안 `[BOARD]` 부록을
> 썼다. 최종적으로 **XCONDA_v1 씬 `.json`**으로 확정됐다. 이유와 스키마는 §13-B와
> `references/scene-json-schema.md`에 있다.

**프롬프트와 데이터는 경쟁하는 산출물이 아니라 한 쌍이다.**

```
편집기 .html  ──(영문 열만)──▶  Seedance
씬 .json      ──(어댑터)────▶  블로킹 보드  ─▶ 사용자 편집 ─▶ 보드 프리셋 저장
```

**교환 포맷과 저장 포맷은 다른 물건이다.** XCONDA_v1은 *Claude의 대본 해석 결과*이고,
보드 프리셋은 *사용자가 손으로 확정한 상태*다. 같은 파일에 담으면 씬을 다시 파싱할 때마다
사용자가 드래그로 고쳐놓은 좌표를 덮어쓴다.

**§20 전체와의 차이**: §20은 사용자가 "블로킹 보드에 등록해줘"처럼 명시적으로 요청했을 때
오브젝트 분류표·크기 추정·코드 스니펫까지 전부 만드는 절차다. 이 §20-1은 훨씬 가볍다 —
**매번 글콘티를 프롬프트로 바꿀 때마다, 아무 요청이 없어도** 씬 JSON을 함께 만든다.
분류표·크기표·코드 스니펫(PROP_SIZES 등)은 여기서 만들지 않는다.

**트리거**: 올린 자료가 **CUT 번호·씬 헤더가 있는 대본/글콘티**인 경우. 채팅창에
"눈밭에서 여자가 체인소로 싸운다"처럼 한 줄 설명만 받았으면 만들지 않는다.

**만드는 법 — 새로 조사하지 않는다**: 방금 채운 DATA 블록(03 시네마틱 셋업 / 04 옵틱스·
카메라 / 05 소품·의상 락 / 08 타임라인)에 이미 적힌 공간 관계를 좌표로 옮긴다. 편집기에
없는 사실을 JSON에서 새로 지어내지 않는다. 편집기의 `【 】` 항목은 JSON에서
`parsing[].needsReview: true`가 된다.

**`source` 두 필드를 반드시 채운다**
- `source.prompt` — 사용자가 올린 글콘티 원문 (재파싱의 근거)
- `source.editorKo` — 편집기 한국어 열 전문 (보드의 텍스트 1차 배치용)

**몇 개를 만드는가**: 이번 응답에서 실제로 편집기로 만든 범위만큼만. 아직 안 만든 나머지
씬의 JSON을 미리 만들지 않는다.

**파일명**: `xconda_scene_[씬식별자].json` — 편집기와 짝을 이루는 이름으로.
예) 편집기가 `xconda_new_editor_s8_partB.html`이면 JSON은 `xconda_scene_s8_partB.json`.

**띄우는 법**: 별도 응답으로 나누지 않는다. `present_files` 한 번에 `.html`과 `.json`을
같이 넣는다. 대화창 브리핑에는 "보드용 씬 JSON도 함께 만들었습니다" 한 줄과, 신뢰도가
낮아 확인이 필요한 항목이 있으면 그것만 짚는다. JSON 본문을 대화창에 옮겨 적지 않는다.

**여기서 멈추는 이유**: 오브젝트를 SPECIES/PROP_SIZES 코드에 실제로 등록하려면 크기(px/m)·
색(hex) 추정과 이름 충돌 검사가 필요한데, 판단이 개입되는 작업이라 자동으로 넘겨짚지
않는다. 응답 끝에 "보드 코드에 직접 등록하고 싶으시면 말씀해주세요"라고 안내만 하고 §20으로
이어지게 한다.
