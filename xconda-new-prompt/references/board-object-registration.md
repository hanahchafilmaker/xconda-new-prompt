# 글콘티/오브젝트 정리 문서 → 블로킹 보드 등록 규칙

> 이 문서는 SKILL.md §20에서 호출된다. 초보자도 그대로 따라 할 수 있도록 용어를 풀어서 쓴다.
> "블로킹 보드"란 `index.html`(+ `app.js` 등)로 이루어진, 인물·소품·카메라를 화면 위에서
> 드래그로 배치해보는 3D 미리보기 도구를 말한다. 이 문서는 그 도구의 코드에 새 사물을
> 등록하는 법을 다룬다.

---

## 0. 먼저 알아야 할 것 — 이 보드가 크기를 재는 단위

- **px(픽셀)**: 화면에 그리는 단위. 이 보드는 **40px = 실제 1m**로 정해놨다. 즉 실제 크기가
  0.4m면 16px로 쓴다.
- **m(미터)**: 실제 키·높이. 3D 화면과 "발밑 높이 계산"에 쓰인다.
- **hex 색상**: `#`으로 시작하는 6자리 코드(예: `#2b2b2d`는 짙은 검정에 가까운 회색). 정확한
  색을 몰라도 재질로 짐작해서 고르면 된다 — 쇠붙이는 어두운 회색, 나무·가죽은 갈색 계열,
  금동 유물처럼 광택 있는 놋쇠색은 `#a3825a` 같은 색.
- **diff(디프) 표기**: 코드에서 "새로 추가되는 줄" 앞에 `+`를 붙여 보여주는 표기법. 실제
  파일에 `+`가 들어가는 게 아니라, "여기에 이 줄이 새로 생긴다"는 뜻의 설명용 표시다.

## 1. 다섯 갈래 분류 — 이것부터 정확히 나눈다

오브젝트 정리 문서에 범례가 있으면(예: 🧍 인물 · 🪑 소품 · 🏚 장소 · 🔦 장비 · 👁 특수 요소)
그걸 참고하되, 최종 판단은 아래 기준을 따른다. **장비(🔦)는 대부분 소품과 같은 방식으로
등록한다** — 범례가 나눠놨어도 코드 등록 방식은 소품과 동일하다.

### (A) 사람 배우 — 등록할 코드가 없다
**판별**: 극중 이름이 있고, 실사 인간 형상이며, 대사·행동의 주체.
**처리**: 보드는 `species` 기본값이 이미 `'사람'`이다. 새로 등록할 코드가 전혀 없다 — 프리셋의
`Cast:` / `ACTIVE REFERENCES`에 이름만 적으면 보드가 자동으로 사람 배우로 잡는다.
예: 이현우, 김민희, 방대한, 박수, 곽태성.

### (B) 크리처 — `SPECIES`에 새 종을 등록한다
**판별**: 동물이거나, 사람과 다른 신체 구조의 초자연적 존재. **핵심 판단 기준 하나**: 화면
위에서 위치·이동을 배우처럼 지정해야 하는가? 그렇다면 겉보기에 "특수효과"(👁) 같아 보여도
크리처로 등록한다. (예: "원혼"은 유령/특수효과처럼 보이지만, 실제로는 한 자리에 서 있거나
움직이는 형체이므로 크리처로 등록되어 있다.)

**코드 형식** (`SPECIES` 객체에 추가):
```js
'종이름': { h: 실제키(m), r: 탑뷰반지름(px), icon: '이모지' },
```

**크기 추정법** — 실제로 등록된 값들로 감을 잡는다:

| 크리처 | h(키, m) | r(탑뷰 반지름, px) | r/h 비율 |
|---|---|---|---|
| 사람(기준) | 1.70 | 20 | 11.8 |
| 이무기(깡철이, "손바닥만 한 도마뱀") | 0.30 | 9 | 30 |
| 삼두매(머리 셋 달린 매, 사람 키만 함) | 1.85 | 22 | 11.9 |
| 원혼(사람 형체) | 1.72 | 16 | 9.3 |

**요령**: 사람과 비슷한 크기(1.5~2m대)면 비율 10~12 정도로 계산한다(예: 키 1.8m면
r ≈ 1.8×11 ≈ 20px). 아주 작은 생물(도마뱀·쥐 등)은 비율을 크게(20~30) 잡아야 화면에서
너무 작아 클릭도 안 되는 사고를 막는다 — 최소 반지름은 8px 이상을 권장한다.
**icon**: 정확히 맞는 이모지가 없으면 형태가 비슷한 걸로 대체한다(도마뱀 몸통의 생물 →
🦎, 새·매 계열 → 🦅/🐦).

### (C) 소품(prop) — `PROP_SIZES` · `PROP_H` · `PROP_C` 세 곳에 등록한다
**판별**: 인물이 들거나 공간에 놓이는 물체(무기·장비·서류·가구·차량 등 전부 포함).

**코드 형식** (세 객체에 각각 추가, 이름은 반드시 동일하게):
```js
// PROP_SIZES — [가로px, 세로px], 40px = 1m
'물건이름': [가로, 세로],
// PROP_H — 실제 높이(m). 세워진 물체 기준.
'물건이름': 높이,
// PROP_C — 색상 하나 (hex)
'물건이름': '#헥스코드',
```

**크기 추정 예시** (실제 등록된 값 — 비슷한 물건을 찾아 비교해서 유추한다):

| 물건 | PROP_SIZES(가로,세로 px) | PROP_H(m) | PROP_C |
|---|---|---|---|
| 권총 | [12, 3] | 0.06 | `#2b2b2d` (짙은 쇠) |
| 소총 | [92, 6] | 0.16 | `#33343a` |
| 방탄조끼 | [26, 20] | 0.9 | `#4a4e50` |
| 캠코더 | [18, 10] | 0.12 | `#2b2d31` |
| 금동대향로(놋쇠 유물) | [24, 24] | 0.55 | `#a3825a` (놋쇠색) |
| 부적(종이, 아주 얇음) | [16, 22] | 0.02 | `#c9b46a` |
| 철제캐비넷 | [30, 22] | 1.8 | `#55585c` |
| 승합차(밴) | [200, 84] | 1.95 | `#6b7480` |

**바닥에 눕는 얇은 물건**(부적·서류·사진 등)은 `PROP_H`를 0.02~0.05m처럼 아주 낮게 준다 —
실제 두께가 아니라 "바닥에서 얼마나 떠 보이는가"의 문제이기 때문이다.

**차량은 특별 취급**: `자동차`(일반 승용차)와 `승합차`(밴, 창문 여러 개인 긴 차체)를
반드시 구분해서 쓴다 — 같은 장면에 밴만 있으면 "자동차"는 안 써도 되지만, 대본에 "승합차"라고
적혀 있는데 코드에 "자동차"로 잘못 등록하면 안 된다.

### (D) 장소(room/set) — `ROOM_SIZES`와 `ROOM_PRESET` 두 곳에 등록한다
**판별**: 씬이 벌어지는 공간 자체(건물 내부, 골목, 승강장 등). 인물이나 소품이 아니라
"무대 배경"에 해당하는 것.

**코드 형식**:
```js
// ROOM_SIZES — [가로px, 세로px]. 비슷한 규모의 기존 장소와 비교해서 정한다.
'장소이름': [가로, 세로],

// ROOM_PRESET — 그 장소에 기본으로 딸려오는 소품 배치 목록
'장소이름': [
  ['소품종류', x좌표, y좌표, 회전각],
  ...
],
```
- x, y는 장소 **중심(0,0) 기준 상대좌표**(px), 회전각은 도(°) 단위(0°가 기본 방향, 90°는
  옆으로 90도 돌린 것).
- **중요한 제약**: 여기 쓰는 `'소품종류'`는 반드시 (C)에서 `PROP_SIZES`에 이미 있거나 이번에
  같이 추가한 이름과 **정확히 똑같은 글자**여야 한다. 한 글자라도 다르면(예: "철제캐비넷" vs
  "캐비넷") 보드가 그 소품을 못 찾아서 화면에 안 나타난다.

**예시** (무기보관실 — 폭 300px×260px, 캐비넷 3개 + 무기 배치):
```js
'무기보관실': [300, 260],   // ROOM_SIZES

'무기보관실': [              // ROOM_PRESET
  ['철제캐비넷', -90, -80, 0], ['철제캐비넷', 0, -80, 0], ['철제캐비넷', 90, -80, 0],
  ['권총', -60, 30, 90], ['소총', 10, 30, 90],
  ['금동대향로', 100, 90, 0], ['문', 120, -120, 0], ['부적', -120, 90, 0],
],
```

### (E) 특수 요소/비주얼 이펙트(👁) — 원칙적으로 등록하지 않는다
**판별**: 물체가 아니라 화면 효과(공간 균열, 붉은 실금 문양, 안개, 소리 등).
**처리**: 코드에 등록하지 않는다. 프롬프트 산문(01번 SCENE CONTEXT, 03번 시네마틱 셋업 등)
에 텍스트로만 남긴다. 단, (B)에서 설명했듯 **화면 위 위치를 배우처럼 지정해야 하는 것**이면
크리처로 등록해야 한다 — 헷갈리면 "이 효과가 한 자리에 서 있거나 이동하는 하나의 형체인가,
아니면 화면 전체·배경에 걸쳐 있는 효과인가"로 판단한다. 전자면 크리처, 후자면 비등록.

## 2. 이름 충돌 검사 — 코드를 만들기 전에 반드시 먼저 한다

사용자가 보드 코드 파일(`app.js` 등)을 함께 올렸으면, 새 이름을 등록하기 전에 그 파일
안에서 같은 이름이 이미 있는지 검색부터 한다(예: `grep -n "'물건이름'" app.js`). 이미
있으면 새로 추가하지 않고 "이미 등록되어 있습니다"라고 보고한다.

파일이 없으면 이 단계를 생략하고, 결과물 맨 앞에 "app.js가 없어서 기존 등록과 충돌하는지는
확인하지 못했습니다 — 실제 파일에 붙여넣기 전에 같은 이름이 있는지 한 번 검색해보세요"라고
분명히 적는다.

## 3. 코드 스니펫 출력 형식 — "추가분만" 준다

사용자의 `app.js`는 이미 수천 줄일 수 있다. **파일 전체를 다시 쓰지 않는다** — 그러면 기존에
등록된 다른 오브젝트들이 통째로 사라지거나 뒤섞일 위험이 있다.

항상 "어느 객체의, 어느 줄 다음에, 무엇을 추가하는지"를 diff 스타일로 보여준다:

```diff
// PROP_SIZES 객체 안, 마지막 줄(전선 항목) 다음에 추가:
+ '까마귀둥지': [10, 10],
```

**실제로 파일을 고쳐줄 때**(사용자가 app.js를 올려서 str_replace 도구로 바로 편집할 수 있을
때)는, `old_str`에 **그 파일에 실제로 있는 줄을 그대로** 복사해서 넣어 정확한 위치에
삽입한다 — 짐작으로 앵커 텍스트를 지어내지 않는다.

## 4. 씬 JSON 생성 형식 (구 프리셋 .txt — v6에서 폐지)

> **⚠️ v6에서 바뀐 것**: 프리셋 `.txt` 산출물은 폐지됐다. 좌표·동선 데이터는 이제
> **XCONDA_v1 씬 `.json`**에 담는다 — 규격은 `references/scene-json-schema.md`, 실례는
> `examples/template_scene_v1.json`. 아래 남은 내용 중 **미터→px 환산 규칙과 크기·색
> 추정 기준은 그대로 유효**하며, 어댑터가 그 값을 쓴다. 텍스트 블록 순서(SCENE CONTEXT →
> ACTIVE REFERENCES → …)는 JSON의 `source.editorKo`에 편집기 한국어 열을 옮겨 담는
> 것으로 대체됐다.

반드시 XCONDA 편집기가 뽑는 프롬프트와 **완전히 같은 블록 순서**로 쓴다:

```
SCENE CONTEXT
ACTIVE REFERENCES
LOCATION MAP AND LIGHTING
FORMAT MODE
OPTICS
CAMERA
PROP LOCK:
Wardrobe:
BACKGROUND CAST
ACTION TIMELINE
```

실제 형식·문장 톤은 `examples/template_scene_v1.json`을 열어 그대로 따라 쓴다 (내용만 새 장면에
맞게 새로 쓰고, 블록 이름이나 순서는 바꾸지 않는다).

**본문 뒤에는 반드시 `@board` 좌표 부록을 마지막 섹션으로 붙인다** — 자세한 필드 규격은
`SKILL.md` §20-1-A를 따른다. 이 부록은 씨댄스용 본문 문법과 완전히 분리된 **블로킹 보드 전용
머신 마커**이며, 절대 씨댄스 프롬프트(본문 위쪽)에는 섞이지 않는다:

```
## @board 좌표 부록 (블로킹 보드 배치용 — 씨댄스에는 넣지 않는다)

BLOCKING
Gwak:
  @board(x=16,y=5.3,hdg=90,motion=114_05)
Daehan:
  @board(x=16,y=10.8,hdg=-90,
         keys=0/16/10.8/104_02;0.4/16/8.6;0.65/16/6.5,
         khdg=0/-90;0.65/-90,
         markers=0:pose:서다;5:104_02;65:pose:서다)

SETBOARD
ROOM 집무실 @board(x=16,y=9,w=24,h=15)
PROP 책상 @board(x=16,y=7.5,hdg=0)

CAMBOARD
CUT14-1 @board(x=11,y=13,h=1.6,hdg=135)
```

**필드 요약** (전부 미터(m) 단위, 좌표계는 +x 오른쪽·+y 아래쪽):

| 블록 | 필드 | 의미 |
|---|---|---|
| `BLOCKING` (인물) | `x,y` | 위치(m) |
| | `hdg` | 방향(도). 0°=오른쪽(+x), 90°=아래쪽/남쪽(+y), 180°=왼쪽(-x), -90°/270°=위쪽/북쪽(-y) |
| | `path` | 동선 경유점. `x/y/도착시각(0~1)`을 `;`로 연결 |
| | `keys` | 키프레임. `시각/x/y/모션클립ID`를 `;`로 연결 (모션클립 생략 가능) |
| | `khdg` | 키프레임별 시선 방향. `시각/hdg`를 `;`로 연결 |
| | `motion` | 정적 모션캡처 클립 ID 1개(서다·앉다 등) |
| | `markers` | 모션 타임라인. `시각%:클립ID` 또는 `시각%:pose:자세이름`을 `;`로 연결 |
| | `ride` | 차량 탑승. `차종/하차시각(0~1)/좌석(L 또는 R)` |
| `SETBOARD` (장소·소품) | `ROOM <종류> @board(x,y,w,h)` | 장소 중심 위치 + 가로세로 크기 |
| | `PROP <종류> @board(x,y,hdg)` | 소품 위치 + 방향. 같은 종류가 여럿이면 `#2`,`#3`처럼 이름 뒤에 번호를 붙여 구분 |
| `CAMBOARD` (카메라) | `<라벨> @board(x,y,h,hdg)` | 카메라 위치 + 눈높이(h, m) + 방향 |

모션클립 ID는 `references/mocap-library.md`(1,456개 카탈로그)에서 실제 존재하는 ID를
확인한 뒤 쓴다 — 카탈로그에 없는 ID를 지어내지 않는다. 어떤 클립을 써야 할지 확신이 없으면
`motion`/`keys`/`markers` 필드를 아예 비우거나 값 뒤에 `【추정】`을 붙여 남긴다 (§6의 불확실
항목 표시 원칙과 동일).

`path`/`keys`/`ride`는 대본에 실제로 그 동작이 적혀 있을 때만 채운다 — "뒷모습으로 Frame
In하는 대한이 책상 앞으로 다가와 보고서를 내려놓는다"처럼 이동이 명시된 경우엔 `keys`로
옮기고, 그냥 "앉아있다"처럼 정지 상태면 `x,y,hdg`(+선택적으로 `motion`)만 쓴다.

**어떤 씬을 프리셋으로 만들 것인가**: 오브젝트 정리 문서에 "★메인" 표시나 "핵심 씬 요약"
섹션이 있으면 그 씬들을 우선 만든다. **문서에 나온 모든 씬을 한 번에 다 만들지 않는다** —
사용자가 "전부 만들어줘"라고 명시하지 않는 한 핵심 씬 3~5개로 먼저 시작하고, "이 외에 더
필요한 씬이 있으면 말씀해주세요"라고 한 줄 덧붙인다.

## 5. 결과물 구성 — 항상 이 순서로 낸다

1. 분류표 (사람/크리처/소품/장소/특수효과, 애매한 항목은 `【 】`로 표시)
2. 크기·색 추정표 (px/m/hex)
3. 이름 충돌 검사 결과 (또는 "검사 생략" 안내)
4. 코드 스니펫 (diff 스타일, 객체별로 나눠서)
5. 프리셋 .txt 파일들 (핵심 씬 우선)
6. README/GUIDE에 이어 붙일 수 있는 표 형식 안내 문구 (있는 표 형식 그대로 이어 쓴다 — 새
   섹션 제목을 새로 만들지 않는다)

## 6. 자주 하는 실수

- **px와 m을 헷갈림**: `PROP_SIZES`는 px(40px=1m), `PROP_H`는 m. 같은 물건인데 단위를 섞어서
  쓰면 화면에서 크기가 어긋난다.
- **ROOM_PRESET에 쓴 소품 이름이 PROP_SIZES에 없음**: 반드시 먼저 (C) 소품 등록을 끝내고
  나서 (D) 장소의 기본 배치를 쓴다.
- **얇은 물건에 두꺼운 높이를 줌**: 부적·서류·사진처럼 눕는 물건은 `PROP_H`를 0.02~0.05m로.
- **크리처인지 소품인지 헷갈림**: "그 대상이 스스로 움직이는가?"가 기준이다. 스스로 움직이면
  크리처(SPECIES), 사람이 들거나 배치해야만 움직이면 소품(PROP_SIZES).
- **승합차/자동차 혼동**: 밴(창문 여러 개, 긴 차체)은 승합차, 일반 승용차는 자동차로 정확히
  구분한다.
